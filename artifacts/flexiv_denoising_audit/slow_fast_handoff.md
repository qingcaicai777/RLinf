# 慢响应与快响应的 chunk 交接差别

本次排查解释在调度固定时，约 300 ms 的响应与约 105 ms 的响应为何可能呈现不同的交接抖动。24/18 的配置修改不作为这个现象的原因。

机器人运行循环以当前 tick 选择动作；推理响应时间不会暂停全局 tick。新预测的时间起点是请求观测帧，服务端先按预定边界切片。客户端迟到后仍按当前 tick 减预定边界选择切片中的动作，不从切片第一项重新开始。

以同一个 22/18、30 Hz 调度和 request frame=18 为例：

| 行为 | 响应约 105 ms | 响应约 300 ms |
|---|---|---|
| 预定边界 | tick 22 | tick 22 |
| 实际接入 | tick 22 | 约 tick 27，取决于完成时间和 tick 检查 |
| 第一个实际发送的新预测索引 | 4 | 约 9 |
| tick 22～26 | 连续发送新预测 | action=None，重复发送旧目标 |
| 切换前运动 | 连续执行目标序列 | 已有约 167 ms 的目标保持 |

这说明比较两种响应时，执行动作、接入索引和控制器在边界处的运动状态均发生变化。旧版本迟到还可能清空下一轮 RTC；若 300 ms 对应 15 步去噪，采样结果也同时改变。没有当时的 conditioned 和 handoff 日志，不能确认各因素分别贡献多少。

已收到的快响应日志均 late_ticks=0，边界命令跳变为 0.47～0.73°。这是实际发送目标的突变证据，不是实测机械臂振荡证据。当前 RTC 通过有限强度的 clean-action VJP 引导旧计划；权重为 1 也不代表输出被锁定到旧动作，执行切换位置通常还落在 soft mask 区域。它没有强制交接位置或速度连续。

控制器端每帧 SendJointPosition 的终点速度为零，并使用速度、加速度约束；推理端下一次观测则读取实际 q。若实际 q 尚未追上旧命令，最新观测驱动的新预测可能相对旧计划回撤，在 chunk 边界表现为目标方向或步长改变。迟到后的保持可能缓解跟踪偏差或让控制器减速，因此降低可见冲击；这仍是待测假设，不能推断保持 167 ms 后必然到达目标或完全静止。

已补充两项只读日志：

- coarse chunk entry：实际 first_prediction_index 和 held_ticks，验证慢响应是否真的经历保持与前缀跳过。
- joint request tracking：使用已有 observation，记录最后命令与实测 q 的 max_command_tracking_error_deg，验证控制器是否持续落后于命令。

下一轮诊断应固定调度、checkpoint 和去噪步数，结合这两项日志及 joint handoff、joint prediction continuity、inference RTC。若快响应下跟踪误差明显且边界发生回撤，应优先追踪观测状态与命令计划的偏差；若跟踪误差很小而同一时刻两次预测差异仍很大，应优先排查采样与 RTC 引导。仅靠增加等待或降低推理频率，不能验证或消除这些原因。

本次修改没有增加等待、滤波、动作混合或机器人 SDK 查询，没有更改调度。扩展现有运行时测试，验证准时接入、迟到保持和跳过过期前缀的实际行为。
